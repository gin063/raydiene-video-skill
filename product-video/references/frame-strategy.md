# 帧策略 · 首帧与尾帧

本文是这套 workflow 里**唯一不能靠常识推出来**的部分。写 prompt 之前必须理解清楚。

---

## 1. 首帧和尾帧到底是什么

我们生成的不是「两张好看的图」，而是**一段视频的两个端点**。

```
首帧图 ────────── 视频模型补全中间过程 ────────── 尾帧图
（现象开始前              ↑                    （现象结束后
  的最后一刻）      过程描述在这里，              的第一刻）
                   由视频 prompt 承载
```

三段内容严格分工，**不许重叠**：

| | 承载什么 | 由谁写 |
|---|---|---|
| 首帧 prompt | 现象**尚未发生**时的完整画面 | 图像模型 |
| 尾帧 prompt | 现象**已经发生完**时的完整画面 | 图像模型 |
| 视频 prompt | 从前者变成后者的**过程** | 视频模型 |

## 2. 首帧的判定标准

**问自己一句：这一帧里，那件事开始了吗？**

开始了就是写错了。首帧要的是**临界点前的静止态**——所有条件都已就位、张力已经拉满、但事情还没发生的那一瞬。

| 现象 | ❌ 写成了过程中 | ✅ 临界前的定格 |
|---|---|---|
| 雨淋桩体 | 雨水冲刷着桩体表面 | 桩体表面完全干燥，云层压暗天光，第一滴雨刚在桩体顶部留下一个深色圆点 |
| 灰尘吹过 | 灰尘扑向桩体 | 空气静止，一团扬尘刚从画面右缘进入，尚未接触桩体，桩体表面洁净无尘 |
| 指示灯亮起 | 指示灯闪烁着 | 指示灯完全熄灭，灯罩内可见未通电的灰暗导光柱 |
| 人靠近解锁 | 人走向车辆 | 人站在距车约 4 米处，脚步刚落地，车灯未亮，桩体屏幕处于待机 |
| 继电器拆解 | 外壳正在分离 | 继电器完整闭合，外壳接缝清晰可见，尚无分离间隙 |
| 断电保护 | 红光蔓延 | 三个监测图标均为常亮绿色，桩体状态正常，无任何异常提示 |

**「尚未接触」「刚落地」「接缝清晰但无间隙」这类措辞是首帧的标志。** 它们描述的是位置和状态，不是动作。

## 3. 尾帧的判定标准

尾帧是**现象走完之后的第一刻**，不是「很久以后」。

| ❌ 跳太远 | ✅ 刚结束 |
|---|---|
| 雨停了，地面已经干 | 桩体表面布满流水，水珠沿下缘串成线并将坠未坠，地面积起薄水膜 |
| 车已经开走 | 车灯双闪刚熄，桩体屏幕点亮显示「已连接」，人的手刚触到充电枪 |

尾帧和首帧之间的时间跨度，就是这个镜头的时长。**镜头 3 秒，尾帧就该是 3 秒后的样子**，不是 30 秒后。

## 4. 尾帧 prompt 怎么写：只做增量

🔴 **尾帧 prompt 不是重新写一遍，是把首帧 prompt 整段复制过来，只替换发生了变化的那几句。**

场景、机位、焦段、光圈、布光、色温、构图、质感——**逐字不动**。

```
首帧 prompt ──── 复制 ────> 尾帧 prompt
                              ↓
                     只改：主体状态那 1-3 句
```

理由不是省事。首尾帧最大的失败模式不是「画得不好」，是**除了该变的之外还变了**：机位飘了、光位偏了、桩体细节不一致、地面材质换了。接成视频就是一次生硬跳变，比不做首尾帧还糟。

配套两条操作约定（属于操作者，但写 prompt 时要意识到）：
- 生成尾帧时，**把首帧图一起作为参考上传**
- 尾帧 prompt 里的产品参考句照写不误，不能因为「首帧已经有了」就省掉

### 🔴 「只改几句」是写作纪律，不是交付格式

**交付出去的尾帧 prompt 必须是完整全量的、可以整块复制的文本。**

绝对不要写成「复制首帧，把第 N 段替换为……」。那样看着省 token，实际是把拼接和重组的
成本转嫁给了操作者——而且每多一次人工拼接，就多一次漏改、错位的机会。

两件事分清楚：
- **写的时候**：从首帧整段复制，只动变化的那几句。这是保证不漂移的纪律。
- **交出去的时候**：完整一整段，操作者复制即用。

一个附带的坑：尾帧真正要改的**常常不止「主体状态」那一段**。首帧无文字、尾帧有文字时，
禁止项里那句「除 X 外不要出现任何文字」要跟着改；对焦点、光线、构图重心也可能因为变化量
而必须微调。全量写出来时这些自然就对上了，增量写法则很容易漏掉。

## 5. 一个镜头只能有一个变化量

首尾帧之间只允许存在**一条变化线**。

> ❌ 首帧：桩体干燥、灯灭、人在远处
> 　 尾帧：桩体湿透、灯亮起、人已到车旁
>
> 三个变化量。视频模型不知道谁先谁后，会同时推进或随机排序，出来是一团糊。

正确做法是**拆镜**：

| 镜号 | 变化量 |
|---|---|
| S03 | 桩体从干燥到布满流水 |
| S04 | 指示灯从熄灭到亮起 |
| S05 | 人从远处到车旁 |

拆镜不额外花钱——本来就要出图，只是分成三组。而合成一个镜头的返工才是真花钱。

**例外**：多个变化量如果是**同一个因果链上的必然结果**，可以合并。比如「插枪 → 指示灯亮」是一个动作带来的，算一个变化量；「插枪 + 天开始下雨」是两件事，必须拆。

## 6. 首帧 only 还是首尾帧

用户的原则是：**要收敛用首尾帧，要发散用首帧。** 落到判据上：

### 必须首尾帧（收敛）

- **产品外观必须全程稳定** —— 只要产品在画面里占比可观，就走首尾帧。单张首帧无法约束视频模型不去改动 logo、配色、比例
- **有明确的状态变化** —— 灯灭→亮、干→湿、闭合→分离、绿→红
- **有精确对齐的时长要求** —— 要卡台词、卡音效、卡剪辑点
- **画面内有文字/数字，且必须准确** —— 尾帧图把最终文本锁死，视频模型只需过渡

### 可以只要首帧（发散）

- **氛围空镜、环境铺垫** —— 车库全景、雨夜街道，没有具体要交代的状态变化
- **纯粒子/光效** —— 扬尘飘散、雨丝落下、光晕流动，过程本身就该随机
- **希望模型自己想出运动方式** —— 探索阶段，先看几版再决定要不要收

### 拿不准的时候

**默认首尾帧。** 多画一张图的成本，远低于视频里产品变形一次的成本。

⚠️ 走首尾帧前先确认目标模型支持。Kling 3.0 原生支持首尾帧；即梦社区主流 skill 则明确弃用首尾帧、
改走多图参考。见 `model-routing.md` 第 3 节的分流表。

## 7. 运镜归谁管

🔴 **走首尾帧的镜头，运镜不写进视频 prompt。**

首尾帧已经把起止构图钉死了。再在视频 prompt 里写「缓慢推进」，等于给了模型两套互相矛盾的指令——推进量到底听图的还是听文字的。结果通常是先推进再拉回，或者干脆无视尾帧构图。

**运镜由两张图的构图差值隐含表达，让模型自己走通。**

想要推镜，就把尾帧的景别做得比首帧更近；想要摇镜，就让尾帧的主体位置偏移；想要环绕，就让尾帧换一个方位角。模型会自己算出中间路径。

**只出首帧的镜头**是唯一例外——那时没有第二个端点可以推断，运镜必须写在视频 prompt 里。

## 8. 落到镜头表上

每个镜头至少要能回答这四个问题，答不上来就是没想清楚：

1. 这镜的**变化量**是什么？（一句话，只能有一个）
2. 变化**开始前**画面是什么样？（→ 首帧 prompt）
3. 变化**结束后**画面是什么样？（→ 尾帧 prompt）
4. 中间**怎么变**的？（→ 视频 prompt）

## 9. 连续段：链式首尾帧

前八节说的是**单个独立镜头**。当一批镜头属于同一个连续段（要考虑画面连续性和转场）时，多一条规则。

### 先判断：独立还是连续

| | 独立镜头 | 连续段 |
|---|---|---|
| 特征 | 各镜用在成片的不同时间点，中间隔着别的内容 | 首尾相接，观众看到的是一段不断的画面 |
| 镜间关系 | **无需一致**——场景、光线、机位可以完全不同 | 必须承接，否则一眼是拼的 |
| 怎么做 | 各镜独立走 1–8 节 | 本节 |

⚠️ **需求方给的一段文案里，两者常常混在一起。** 确认单里必须逐段标明归属
（`shot-planning.md` 第 1 节的「连续性归属」字段），不要默认全片连续，也不要默认全片独立。

### 链式首尾帧

连续段里，**上一镜的尾帧图直接用作下一镜的首帧图**。

```
S11首帧 ─S11─> S11尾帧 ═ S12首帧 ─S12─> S12尾帧 ═ S13首帧 ─S13─> …
   图1            图2                     图3                  图4
```

N 个镜头只需要 **N+1 张图**，不是 2N 张。而且镜间零跳变——因为衔接处根本就是同一张图，
不是两张"画得很像"的图。

三条配套要求：
- **中间那些图既是尾帧又是首帧**，写 prompt 时两个身份都要成立：它得是上一个变化的终点，
  同时是下一个变化的起点。这是链式最难的地方，也是它值钱的地方
- **整条链共用同一段场景/机位/布光描述**，逐字复用，只有主体状态在推进
- 链条越长，误差越会累积。**超过 5–6 环就考虑断成两条链**，接缝放在成片本来就要切的地方

### 更优解：交给模型一次生成

Kling 3.0 的 **Custom Multi-Shot** 可以一次生成多镜头连续段，转场由模型内部完成。

**连续段优先走这条**，理由有二：转场质量高于外部拼接；且绕开了下一节的时长下限问题。
写法见 `video-prompt.md` 第 7 节。

链式首尾帧留给两种情况：目标模型不支持多镜头；或者每一镜的构图都必须被精确控制、
不能交给模型规划。

## 10. 时长下限：低于 4 秒的分镜不要单独生成

| 来源 | 约束 |
|---|---|
| Kling 3.0 / Omni | 3–15 秒可变 |
| Seedance 2.5 | 单次 4–30 秒；超长模式 30–180 秒 |

**取严的那个：4 秒。**

需求方按台词切的分镜，常常一镜只有 1–2 秒（「漏不漏电，」5 个字约 1.1 秒）。这类分镜
**不能一镜一次生成**，三条出路：

1. **合并生成再剪**（推荐）——相邻几个短镜合成一次 5–10 秒的生成，剪辑时切开
2. **Custom Multi-Shot**——把这些短镜作为 `Shot 1/2/3…` 写进同一次生成，模型自己安排转场
3. **按 4 秒生成后掐头去尾**——最保险但最贵，每镜都要单独出图和生成

节奏卡得紧的段落用 2，画面差异大的用 1，非要逐镜精确控制才用 3。
